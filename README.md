# Today One

「今日は、これだけ。」— 状態に合わせて健康行動を1つだけ提示するアプリ。

`index.html` を開くだけで動きます。ビルド不要、外部通信なし、記録は端末内（localStorage）にのみ保存されます。

- **アプリ**: [`index.html`](index.html)
- **事業戦略提案書**: [`docs/strategic-proposal.md`](docs/strategic-proposal.md)

---

## これは何か

画面に見えるのは「今日やる行動1つ」ですが、本体は行動データが毎日ルールを書き換える**閉ループの意思決定エンジン**です。

```
Action Library → [Health Value Gate] → Context → Execution Fit → Today One
→ 実行/未実行 → [Reason Classifier] → Rule Update ─┐
     ↑                                              │
     └──────────────────────────────────────────────┘
```

角括弧の2つが、競合が持たない部分です。

### Health Value Gate

健康価値が **70/100 未満の行動は、どれだけ楽でも提示しません**。ライブラリには「SNSを5分だけ見る」（12点）のような、簡単だが健康価値のない候補を意図的に残してあり、Gate が実際に効いていることを管理コンソールから監査できます。

閾値は `Object.freeze` された定数で、実行時に変更できません。プランや課金状態で緩めることも設計上できません — **価格は下げても、基準は下げない**。

### Reason Classifier

「今日は難しい」は離脱の逃げ道ではなく、**本製品における主要なデータ採取装置**です。6分類の理由を必ず1つ回収するため、未実行が最も情報量の多いラベル付きデータに変わります。「文脈 → 提示行動 → 実行可否 → 理由」の4つ組が、後発に模倣できない資産になります。

### 「変える」画面が、実は差別化の実体

他社の継続系アプリは「今日はできなかった」を記録して終わります。Today One はそこで健康価値の基準を落とさない代替案を出し、実際に実行へ変えます。90日分のエンジンを実測したところ、**実行できた日の25.0%、「今日は難しい」と言った日の46.4%は、この画面から生まれていました**。管理コンソールの「エンジン」タブにこの内訳を出しています（`m.kaeru`）。

無料プランは固定プログラム（Gate 通過済み・状態には合わせない）、有料プランは状態適応＋「変える」。安全性はどちらも同じで、差が出るのは「その日に合わせて変える力」だけです。詳細は提案書の第3章。

**プラン（`state.plan`）と日次のランダム割付（`arm`）は別レイヤーです。** 前回、既存の Adaptive/Fixed 区分（H1測定用の日次ランダム割付、30%の確率で対照群）をそのまま無料/有料の境界に使えると提案しましたが、これは誤りでした。同じ確率変数を流用すると、無料利用者が70%の確率で有料機能を受け取り、有料利用者が30%の確率で無料体験に落ちる、という両方向の事故になります。`plan`（利用者に固定・free/premium）を `arm`（日次・測定用）の上位レイヤーとして分離し、free は常に固定でランダム割付の対象外、premium の中でだけ測定用の割付が働くようにしました。管理コンソールの「実験ゲート」タブから free プランをプレビューできます。

## 数値を捏造しない設計

このアプリは、**根拠のない数字を一切表示しません**。

| 状況 | 表示 |
|---|---|
| 実データなし | すべての指標が「判定不能」 |
| 個人ルールの各群が5日未満 | 「学習中」。スコアに一切反映しない |
| 群間の差が10pt未満 | 「差なし」。反映しない |
| H1 の各アームが20件未満 | 「判定不能」 |
| 週次の率 | 必ず母数（n日）を併記。n<3 の週はバーを薄く表示 |
| デモデータ投入後 | 全画面に生成データである旨の警告 |

判定が仮説と**逆方向**に出た場合も、その向きのまま採用します（都合のよい向きだけを採らない）。

## 実験設計（H1 の測定）

既定では日ごとに 50% の確率で**固定プログラム（対照群）**を提示します。対照群の日は、文脈を無視した曜日固定のメニューを出し、「今日は難しい」を押しても**代替案を提示しません**。比較の妥当性を守るための意図的な仕様です。

アプリはこの割付をユーザーに隠しません（「固定プログラム（比較用）」と表示）。管理コンソールから割付を停止できますが、停止すると H1 のデータは増えません。

### 仮説ゲート

| ゲート | 内容 | 成立まで禁止すること |
|---|---|---|
| **H1 Fit** | 状態適応で実行率が上がるか | — |
| **H2 Learning** | 使うほど提案が良くなるか | ML 投資、「AI 搭載」訴求、エンジン供給の商談 |
| **H3 Persistence** | 効果が持続するか | 多年度契約の値引き、営業組織の拡大 |

UI のコピーに「AI」という語を使っていないのは意図的です。H2 が成立するまで、証明していない効能を語らないという方針に沿っています。

## 管理コンソール

`#console` にアクセスし、パスフレーズを入力すると開きます（既定: `todayone-admin`、`CONFIG.ADMIN_PASSPHRASE`）。

> **⚠️ このゲートはクライアント側のデモ用です。** ソースを読める相手には無力です。**本番環境では必ずサーバー側の管理者認証に置き換えてください。**

旧プロトタイプではアバターをタップするだけで誰でも開き、実行率比較・実験仮説・個人ルール・Gate 閾値がそのまま露出していました（提案書10章 P0）。起動経路をタップから外し、パスフレーズを追加したのがこの版です。

タブ構成: エンジン / 学習 / 実験ゲート / Health Value Gate / データ境界

---

## データ境界

- 行動ログは**端末内のみ**。サーバーへ送信しません。
- 事業主・健保組合へ渡せるのは**集計値のみ**。
- 対象者が **5名未満の集計は出力を拒否**します（k-匿名性）。単一端末では常に拒否されます — 仕様どおりの動作です。
- 本人向けのデータ書き出し（JSON）に対応。

この壁は後付けできないため、最初から実装しています。企業導入時に法務・労組を通すための前提でもあります。

## 複数パターンの利用者視点での検証

統計的なシミュレーションとは別に、6つの利用者像で実際にUIを操作し、それぞれの制約特有の破綻点を探しました。

| 利用者像 | 制約 | 結果 |
|---|---|---|
| A. 育休明けの共働き親 | 常に在宅・低体力・5分未満 | 問題なし。最悪条件が続いても14日で8種類の行動を巡回 |
| B. 人工膝関節の65歳 | 恒久的な身体制約（膝への衝撃禁忌） | **欠陥あり** → 修正 |
| C. 夜勤ありの看護師 | 壁時計と生活リズムが一致しない | **欠陥あり** → 緩和 |
| D. 出張の多い営業職 | 文脈が毎日大きく変動 | 問題なし。30日間、例外・提示なしゼロ |
| E. 高モチベーションの健康オタク | 1つでは物足りない | 制約あり（意図的な設計、対応せず） |
| F. デジタル不慣れな75歳 | 英語表記・タップ領域 | **改善点あり** → 修正 |

### B. 見つかった安全上の欠陥（重大）

「体力」はその日の疲労感などを表す一時的な状態で、ケガや持病など**恒久的な身体制約を表現する手段がありませんでした**。人工膝関節が入っている利用者が正直に「体力：高」と答えると、膝に衝撃のある行動（スクワット、階段）が候補に入ることを確認しました。「今日は難しい」で回避してもその日限りで、翌日また同じ行動が出ます。

**対応**: 行動ごとに「体に合わない」と申告できる恒久除外機能を追加しました。申告した行動は、Adaptive・Fixed 両方のアームで二度と提示されません（当初 Fixed アームは曜日固定の直接参照だったため、この除外が効いていませんでした。曜日インデックスをずらして代替する形で対応し、対照群としての「裁量なく決まる」性質は保っています）。進捗画面から一覧の確認・取り消しができます。

### C. 見つかったアルゴリズムの欠陥（学習ルールの交絡）

個人ルールの学習（`derivedRules`）は単純な二群比較で、他の要因を制御していません。「夜勤明けは勤務がなく解放感で実行率が高い」という、時間帯とは無関係な交絡を注入したところ、**「朝が合っている」という誤ったルールが33.3ptの差で確定しました**。実際の原因は時間帯ではなく「休みかどうか」です。

**対応**: 交絡の起きやすい「時間帯」「分野」ルールにのみ、注意書きを追加しました（「所要時間」「移動の有無」は物理的制約に近く、この懸念は小さいため対象外）。根本的な解消には多変量の統計制御が必要で、このアプリの規模では過剰設計と判断し、限界の開示に留めています。

### F. 見つかった改善点（軽微）

UIの日本語表記の中に `TODAY'S ONE` `LIGHTER OPTION` という英語ラベルが残っていました。日本語に置き換えました。また「なぜこれ？」ボタンと状態チップのタップ領域が44px未満で、高齢者や運動機能が低下した利用者には小さすぎました。44px以上に拡大しています。

### E. 対応しなかった点（意図的な制約）

「今日はこれだけ」を押した後、UIに「もう1つ」への導線はありません。エンジン内部では2つ目の候補を算出できますが、到達する手段がない。これは「1日1つ」というプロダクト思想そのものであり、Gate・拒否データという中核資産と表裏一体のため、意図的に対応していません。高モチベーション層への機能追加は、コア体験を薄めるリスクとして提案書の検討事項に留めます。

## 実利用者を想定した検証

「52歳・会社員・特定保健指導対象。平日は時間がなく夜は疲れている。月3〜4回は雨で外出しない。やる気は2週目に落ちる」という利用者像で、90日間を通しでシミュレートしました（アプリの採点式を一切参照しない独立した行動モデルを使用）。

### 結果

|  | n | 実行率 | 提供健康価値/日 | 提示hv平均 |
|---|---:|---:|---:|---:|
| 状態適応 | 51 | 49.0% | 37.1 | 75.9 |
| 固定プログラム | 21 | 33.3% | 26.1 | 80.5 |

実行率リフト **+15.7pt**、**提供健康価値（実行された行動のhv合計）は +42.0%**。適応側は提示する行動の健康価値を平均4.6点譲る一方で、実際に届いた健康価値は4割増えました。**Gate（70点）は一度も割れていません。**

### 検証で見つけて直した欠陥

| # | 欠陥 | 影響 |
|---|---|---|
| 1 | 未開封日が母数から抜けていた | 実行率を **8.9pt 過大表示**。健保に出せば破綻する |
| 2 | Fit採点が余裕時間に比例し、1分の行動が常勝 | 全提示の **64%が同一行動**に退化。22種中7種しか出ない |
| 3 | エンジンが自分の選んだ結果しか観測できない | 移動を伴う行動が90日で3日、**該当ルールが永久に確定せず** |
| 4 | 対照群50%が学習データを半減 | 個人ルールの確定が大幅に遅延 |
| 5 | 「今日は難しい」を繰り返すと2つの行動を往復 | 既に断った行動を再提示 |
| 6 | 91日目以降にプログラム終了状態がない | 「完了まであと44日」が永久に表示され続ける |

修正後: 提示は12種に分散、最悪条件（5分・疲労・外出不可）を14日連続でも8種を巡回、4つの個人ルールすべてが21〜45日で確定します。

### 行動は実際に変わるか

前節の検証は「提案が合っていたか」しか測っていません。行動変容を測るには、習慣形成モデル・アプリなしの対照群・提供終了後の追跡が要ります。40人×3群（アプリなし／固定プログラム／Today One）を、介入90日＋**アプリを外した追跡30日**でシミュレートしました（同一人物・同一の天気と予定で対応比較）。

| | 介入90日 | 追跡30日（全群アプリなし） |
|---|---:|---:|
| 健康価値/日（アプリなし群比） | **+53.7%** | **−1.1%** |
| 完了者（54日以上） | 39/40（アプリなし群 22/40） | — |

**行動はアプリがある間だけ変わり、外すと30日でほぼ元に戻ります。** 習慣形成を極端に強く仮定した感度分析でも、撤去後の優位は最大 +12.6%。しかも習慣を強く仮定するほど介入中の優位は縮みます（+53.7% → +22.6%）。つまり **アプリは習慣を育てているのではなく、習慣の代わりをしている**。教師ではなく足場です。

**効果は自力で続かない人に集中します。**

| | アプリなし | Today One |
|---|---:|---:|
| 行動しにくい層（n=21）の完了者 | 5 / 21 | **21 / 21** |
| 行動しやすい層（n=19）の完了者 | 17 / 19 | 19 / 19 |

**Gate の実際の仕事は労力の再配分でした。** 自力の人が実行した行動の **72.9%** は健康価値70点未満（ストレッチ、水を飲む、体重を測る等）。Today One 経由では **4.9%**。行動量を増やしているのではなく、同じ労力の向き先を変えています。実行率だけを見ていては見えない価値です。

### 探索の強さは実測で決めました

学習のための多様性（直近性ペナルティ）は、届く健康価値と直接トレードオフします。

| ペナルティ上限 | 最頻行動の占有率 | 提示の種類数 | 介入中の健康価値 |
|---:|---:|---:|---:|
| 0 | 90% | 5.7 | +66.6% |
| **8（採用）** | **19%** | **14.2** | **+53.7%** |
| 22 | 20% | 16.2 | +52.9% |

0→4 で退化はほぼ解消し、それ以上上げても多様性は伸びずに価値だけが削れます。当初22にしていたのは過剰でした。8に下げ、4つの個人ルールはすべて23〜45日で確定することを確認しています。

### この検証から出た事業上の判断

- **パイロットの割付は「利用者間」で行うこと。** 同一利用者の中で対照日を設けると、H1（比較）と H2（学習）が資源を奪い合い、学習が遅れます。人単位で分ければ両立します。
- **個人ルールの確定は21日では足りません。** 実測で21〜45日。提案書のKPIを45日に改めました。
- **社外へ出す完了率は暦日ベースで統一すること。** 提示日ベースは必ず高く出ます。
- **「行動が変わります」とは売らないこと。** 実証できているのは「提供している間、健康行動が届き続けます」です。契約は一時金型にせず、実績評価の時点まで提供が続く形にします。効果が足場に依存するという事実は、売り方を誤らなければ継続契約の根拠になります。
- **対象は自力で続かない層に絞ること。** 行動しやすい層はもともと自力で完了します。絞るほど費用対効果が上がります。

## 庭とわたし図鑑（報酬レイヤー）

進捗画面に、実行の積み重ねを視覚化する「庭」と、発見した個人パターンを集める「わたし図鑑」（カード15種、2セット）を追加しました。ユーザーから提供された素材パック2種（庭・カード・バッジ・マスコット等の画像40点、続いてガチャ形式のカード素材24点）を仕様として受け取りましたが、実装は既存のCSS/SVGで作り直しています。

### ガチャ・確率抽選は採用しなかった

2つ目の素材パックは、NORMAL70%/RARE20%/EPIC8%/LEGENDARY2%というレアリティ確率抽選（1日1回まで）を提案していました。これは不採用にしています。

- 最初の素材パック自身のREADMEが「ランダムガチャを主目的にしない」と明記しており、今回の提案はその原則と直接矛盾する。
- 確率で報酬が出る仕組み（変動比率強化）は依存性の高い設計として知られ、「健康価値の基準を落とさない」というこのアプリの中核ポジショニング（Health Value Gate）と方向性が逆になる。
- B2B2Cの主要な買い手（健保組合・企業）に対して、健康施策に射幸性の要素を持ち込むことはコンプライアンス上のリスクになる。
- 一部のカード案（家族のサポート、仲間と一緒に等）は、Today Oneに存在しない社会的機能を前提にしており、実データから解錠を判定できない。

ユーザーと相談し、**確率には頼らず、実データから解錠される「予測できない発見」**として実装しました。以下の15枚は、どのカードもガチャではなく `metrics()` / `derivedRules()` の実データだけで解錠が決まります。

- **自分の攻略法セット（8枚）**: 統計的に確定した個人の傾向（所要時間・時間帯・移動・分野など）。既存の実装。
- **乗り越えた記録セット（7枚）**: 「外に出る一歩」「疲れていても」「忙しい日にも」「10分の壁を越えて」「週3の壁」「また始められた」と、6枚すべて解錠で出現するセット完成カード。いずれも統計的なルール確定を待たず、その日1回の実データ（体力・空き時間・外出可否・所要時間・週内実行数・実行間隔）だけで判定する。

庭にも「発見した傾向」表示を追加し、新しいルールが確定するたびに一輪ずつ点灯します（`state.rulesSeen` で永続化。一度確定した発見は、後でルールの判定が変わっても消えません）。累計30日以上実行すると、実際のカレンダーの月に対応して庭の配色が季節に変わります（春夏秋冬とも現実の月から算出、捏造なし）。

### 「今日の発見」— わたし図鑑を見に行かなくても、その場で見せる

3つ目の素材パックは機能追加ではなく絞り込みの提案で、「完了直後に発見を見せる」「できなかった日にも発見を返す」の2点に集中する、という方向性でした。この2つを実装しています。

- **できた直後**: 今日の行動を記録した瞬間、新しく解錠したカードがあればその場でカード名と説明を表示します（`todaysDiscovery()`。記録前後のカード解錠状態を比較して判定）。新しい解錠がなければ、統計的に一番近いルールがサンプル数であと何回で判定できそうかを示します（あと3回以内のときだけ。方向は断定しません）。それも無ければ、正直に「記録が育っています」とだけ表示します。数字を作りません。
- **「今日は難しい」の直後**: 選んだ理由が今までに何回選ばれたか（実データ）を返します。「明日は軽いメニューを優先します」のような、まだ実装していない未来の約束はしていません。実際にその場で代替案へ切り替わった場合は、その事実（今日この場での調整）だけを伝えます。
- どちらの発見も、その日の記録（`rec.discovery`）に保存するため、画面を離れてまた戻っても同じ内容で表示されます。

実装中に見つけた不具合: 「乗り越えた記録」カードの「外に出る一歩」は、当初 `canGoOut===false`（外出できない）を条件にしていましたが、これはアプリの既定値そのものだったため、初回実行だけで自動的に解錠されていました。`travel===true`（実際に外出を伴う行動を選んで実行した）に条件を直し、既定値では満たされないようにしています。「また始められた」（再開）の判定も、未開封日（記録自体が存在しない日）を配列の要素数で数えていたため空白を検出できておらず、暦日の実差分で計算し直しました。同時に複数枚が新規解錠した場合、当初はレアリティが高い順に表示していましたが、これだと初回実行のような基礎的な発見が、たまたま同時に解錠したレアカードに追い越されて見えなくなる（実測: 初日に「外に出る一歩」が先に出た）ため、カード定義順（基礎→応用の自然な順）で先頭を採用するように直しています。

この検証中、テスト自体が確率的に落ちる現象も見つけました。原因はテストの前提側にあり、対照群（`arm:'fixed'`）は意図的に曜日だけで行動を決め `ctx.canGoOut` を見ない設計（H1測定のための対照群としての性質）のため、「今日は外出できない」設定でも対照群に当たった日は外出系の行動が割り当てられ得ます。「新しい発見が何もないはず」を検証するテストが、この対照群を含めたままだと約30%の確率で偶然「外に出る一歩」を解錠してしまい失敗していました。アプリ側の不具合ではなく、テストを `experimentOn:false`（常に適応型のみ）に固定して意図通りの検証に直しています。

- **画像をそのまま使わなかった理由**: 提供PNGは成長段階名（SEED/BLOOM/INDEPENDENT等）が画像に焼き込み済みで、英語のまま・ダークモード非対応（固定の薄緑背景）でした。ダークモードで見ると背景だけ浮いて見えるほか、以前修正した「日本語UIに英語ラベルが混じる」問題の再発になります。manifest.jsonのデータ仕様（段階名・カードのタイトル/説明/レアリティ）はそのまま採用し、見た目だけ既存デザイントークンで再構築しました。
- **badges/mascotは実装していません**: cards（自分の発見）とgarden（積み重ね）が実質同じ達成を別の見た目で二重に表現するだけだったため、システムを2つ作らず一本化しています。

### 3人の利用者を想定した30日シミュレーション検証

「今日の発見」を実装した後、1ヶ月分の実利用を想定して検証しました。単発のシナリオではなく、実際のUI操作（`#doneBtn`/`#hardBtn`/理由選択/`#useAlt`のクリック）でproductionコードをそのまま30日間駆動させています。日付は `window.Date` を偽装して進め、「アプリを開かなかった日」は該当日を一切 `goto` しないことで、未開封日として正しく欠落させました（`rec` 自体が存在しない状態。「また始められた」判定の前提と一致させるため）。

3人の想定利用者:
- **A: 順調な会社員** — ほぼ毎日開き、平日は15分・週末は30分、雨の日だけ外出不可。
- **B: 波あり** — 3日に2日は体力「低」、2回×2〜4日の未開封（不開封）期間あり。
- **C: 最初苦戦→後半持ち直す** — 最初の10日は空き時間5分・体力「低」が続き、11日目以降に条件が改善。

検証で見つけた問題（実データで再現）: 「今日の発見」の「あと1回で、新しい傾向がわかるかもしれません」という残り回数表示は、サンプル数（`n.yes`/`n.no` それぞれ5件以上）だけを見ており、判定に必要なもう一つの条件（差が10ポイント以上あるか）を見ていませんでした。そのため、残り回数が0に達した瞬間に無言で別の軸の残り回数に切り替わり、「あと1回」を何度も表示したまま実際の答えが返ってこないことがありました。順調な会社員（A）で30日分を追跡したところ、所要時間・移動・分野の3軸はいずれも「差はなかった」という判定（`status:'null'`。これも正しい判定であり、確認に必要なサンプルが集まった結果です）に到達しましたが、それを一度も知らせないまま「記録が育っています」という初日と同じ文言を出し続けていました。4軸すべてに答えが出た後（確認済み・逆転・差なし、いずれの組み合わせでも）も、この文言は事実に反して「まだ育っている」ことを示唆し続けます。

対応: `discoverySnapshot()` にルールの状態（`ruleStatus`）を追加し、`todaysDiscovery()` で「学習中」から今回はじめて答えが出た軸（確認・逆転・差なし、いずれも）を検出したら、それをカード発見と同じ優先度でその場に表示するようにしました（`kind:'rule'`）。差がなかった、という結果も本物の発見として伝えます。さらに、4軸すべてに答えが出きった後は「記録が育っています」を出し続けず、「所要時間・時間帯・移動・分野は、今のところすべて確認済みです」という事実に即した文言（`kind:'settled'`）に切り替えています。

この検証過程で分かった、コードの不具合ではない構造的な特性も記録しておきます: 「わたし図鑑」の攻略法セット（C02〜C08、レア以上）は、いずれも「方向性のある確定結果（確認済み・逆転）」のみを解錠条件にしており、「差はなかった」（`null`）では解錠しません。これはカードの主張（「短時間の達人」等、具体的な傾向の断定）と整合させるための意図的な設計で、変更していません。ただしこの設計の帰結として、行動の成功が所要時間・時間帯・移動・分野のどれとも相関しない利用者（今回のペルソナA寄りの、比較的一貫して実行できるタイプ）は、この4種のカードを継続利用しても解錠できない場合があります。皮肉なことに、最も継続できているタイプの利用者ほど、この報酬から得るものが少なくなりうるという設計上のトレードオフです。「今日の発見」の`kind:'rule'`表示は、カードにならなくてもこの利用者に何かを返す部分的な緩和策ですが、根本的なトレードオフ自体は残っています。

検証方法の制約: このシミュレーション自体に、Playwrightのタイミング起因と見られる非決定性がありました（`Math.random()` はこの経路に一切使っていないことをコード上で確認済みで、Fixed/Control判定を無効化する `experimentOn:false` も設定済みです）。再実行するたびに各軸が確定する具体的な日は数日単位でずれましたが、「学習中の軸が答えを出したら通知する」「4軸すべて出きったら正直な文言に切り替える」という修正後の挙動そのものは、複数回の再実行すべてで一貫して再現しました。3ペルソナ×30日、計90回のページ読み込みを通じてconsole/pageerrorは0件でした。

### 行動前の予告 — 「次に何が分かるか」への期待

複数の外部レビュー（Team Ω / Team α 名義）から、「できた」直後の報酬を強めるより先に、行動を選ぶ**前**から「次に何が分かるか」への期待を作るべき、という提案を受けました。1つ目のレビュー案（庭EXP・カード進捗・発見テキストを束ねた3秒のリザルト画面）は不採用にしています。理由は次の3点です。

- **EXPという新しい数字**: 現在の庭の成長は累計実行日数という実測値のみで動いており、EXPという概念自体が存在しません。追加するには恣意的な変換ルールが必要で、「実データだけで解錠する・数字を捏造しない」という一貫した原則、および「ポイント交換」「複雑なレベル制」を追加しないという既存の制約に反します。
- **カード・庭を主役にしないという提案自身の原則との矛盾**: 発見テキスト・EXPバー・カード進捗を1画面に束ねると、視覚的な比重はむしろカードと庭側に増えます。以前、庭とカードを両方成長させると同じ達成を二重表現するだけだと判断し、あえて一本化した経緯があり、この提案はそれを部分的に巻き戻す形になります。
- **意思決定コストを下げるという評価軸との矛盾**: 毎回3秒のリザルト画面を挟むことは、「今日は、これだけ。」から始まる1タップの動線にもう1ステップ追加することになります。

2つ目のレビュー案（行動の前に「次の発見」の**結論**を予告する。例:「忙しい日でも短い行動なら続けやすそうです」）も、結論部分は不採用にしています。1ヶ月シミュレーションで確認した通り、行動が安定している利用者ほど各軸が「差はなかった」に着地する頻度が高く、結論を予告すると高確率で外れ、直前に直したばかりの「果たされない約束」問題を、完了後よりも目立つ行動前の場所で再発させます。加えて、結論を先に見せること自体が利用者の行動をその仮説に合わせてしまい、学習に使う実データを歪めるリスクもあります。

一方、「軸の名前だけを予告し、結論は言わない」という縮小版は採用しました。今日の画面で、行動を選ぶ前（`rec.done === null`）に、学習中の軸のうち確定まで3回以内に近づいているものがあれば、`🔍 所要時間の傾向が、あと1回でわかるかもしれません` のように軸名と残り回数だけを小さく表示します（`nextDiscoveryPreview()`。既存の`closestLearningRule()`をカード発見後の進捗表示と共有し、判定ロジックの重複・乖離を避けています）。対照群（固定プログラムの日、およびfreeプラン）ではこの記録がルール学習に使われないため、予告自体を出しません（出すと「今日やれば分かる」という誤った期待を作ってしまうため）。新しい画面・新しい概念（EXP等）は追加していません。

Playwrightで、初期状態での非表示・軸名と残り回数の表示・方向を断定していないことのテキスト検証・決定後の非表示・対照群/freeプランでの非表示、の5シナリオを検証、3回連続で安定パス。既存の全回帰テストおよび3ペルソナ×30日のシミュレーションも再実行し、regressionなしを確認。

### 「自立」を、断定から問いに変えた

素材パックの原案は、最上位カードとブランドの長期ビジョンを「Today Oneがなくても自分で健康行動を選べる」という**達成の断定**として設計していました。しかし提案書の行動変容シミュレーション（H3b）は、支援を外すと30日でほぼ元の水準に戻るという逆の結果を示しています。断定のまま実装すると、自分たちの実測データと矛盾する約束を製品の中核メッセージにしてしまうところでした。

ユーザーと相談のうえ、この部分は**断定ではなく問いに変えて**実装しています。

- 庭の最終段階は「大樹」という植物の状態を表す言葉に留め、「自立」という行動主張は付けていません。
- 最上位カード（伝説）は「自分の攻略法」とし、説明文は「提案がなくても選べそうか、試してみる番です」という問いかけにしています。解錠条件も「自立を達成した」ではなく「所要時間・時間帯・移動・分野の4つの傾向がすべて分かった」という、実際に検証可能な意味に絞っています。

### 実データだけで解錠する

カードの解錠条件はすべて `metrics()` / `derivedRules()` の実データから判定し、達成していないものを達成したと表示することはありません。庭の成長段階も「これまでの実行日数の累計」だけで決まり、未実行の日があっても後退しません（素材パックの設計注意「未実行で植物を枯らさない」を維持）。

## 実装の制約

- **クライアント側パスフレーズ**は本物の認証ではありません（上記）。
- **単一端末・単一利用者**が前提です。健保組合パイロットでは、同一組合内で対象者を割り付けてサーバー側で集計する必要があります。
- **健康価値スコア（hv）は暫定値**です。各行動の採点根拠を `hvNote` に持たせてありますが、外部展開の前に専門職のレビューが必要です。
- `localStorage` が使えない環境（プライベートモード等）では記録が保存されませんが、アプリは動作を続けます。
