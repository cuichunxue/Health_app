## エグゼクティブサマリー

1. **売る相手は個人ではなく制度。** 健保組合の特定保健指導と企業の健康経営には既に予算と、行動変容を説明する義務がある。個人課金アプリの消耗戦を避け、B2B2C を主軸に据える。
2. **売る場所は「保健指導の代替」ではなく、その空白。** 特定保健指導は初回面接と実績評価の間に3〜6ヶ月の無人区間がある。Today One の日次1行動という形は、この区間の充填にほぼ専用設計されている。
3. **中核資産は UI ではなく3点セット。** 健康価値を下げない Gate（70/100）、拒否理由を構造化する Reason Classifier、そして両者を毎日回す閉ループ。特に「拒否データ」は競合が持たない学習資産である。
4. **今売れるのは AI ではなく実測リフト。** Adaptive 74% 対 Fixed 61%（+13pt）は既に営業できる証拠。Console 自身が定める H2 成立まで、ML 投資と「AI 搭載」訴求は解禁しない。
5. **着手前に塞ぐ穴が1つ。** 現状はアバターを1回タップするだけで、実行率比較・実験仮説・個人ルール・Gate 閾値を含む内部コンソールが誰にでも開く。

| 指標 | 値 |
|---|---|
| Adaptive 実行率 | 74% |
| Fixed 実行率 | 61% |
| リフト（H1 の実証値） | +13pt |
| Health Value 下限（変更禁止） | 70/100 |

## 01. プロトタイプが実際に作っているもの

ユーザーに見えているのは、体力・時間・場所の3状態から選ばれた行動を1つだけ提示する画面。「なぜこれ？」で選定理由を開示し、「今日は難しい」で6つの障壁（時間・疲労・環境・強度・意欲・家庭事情）を選ばせ、健康価値を落とさない範囲の軽い代替案に差し替える。ここまではよくできた習慣化アプリの UI に見える。

しかしアバターをタップすると開く非表示の Learning Console に、事業の本体が置かれている。Adaptive と Fixed の実行率比較、未実行理由の分布、学習済みの個人ルール（10分以下で +18pt、18〜20時で 78%、自宅完結で 1.4倍、疲労時は低負荷優先）、仮説ゲート H1〜H3、そして次の処理列。

```
Action Library → [Health Value Gate] → Context → Execution Fit → Today One
→ 実行/未実行 → [Reason Classifier] → Rule Update
```

これは画面のモックではなく、行動データが毎日ルールを書き換える**閉ループの意思決定エンジン**である。商品は UI ではなくこのエンジンであり、UI はエンジンにデータを供給する採取装置だと捉えると、以降の判断が一貫する。

## 02. 中核資産は3つ、うち2つは競合が持っていない

### ASSET 1 — 下げないという約束

Console の安全・意思決定欄に、**「Health Value Threshold：70/100／Gate未達：候補から除外／簡単さに合わせた基準変更：禁止」**と明記されている。継続系アプリの大半は離脱を防ぐため達成しやすさを優先し、結果として行動の中身が空洞化する。Today One は負荷を個人に合わせて下げても、健康価値の下限だけは動かさないという思想をコードレベルで固定している。これは開発規約であると同時に、そのまま調達要件への回答であり、対外的な信頼訴求にもなる。

### ASSET 2 — 拒否データという学習資産

ここが最も過小評価されている点。ほとんどの健康アプリにとって「やらなかった日」は失われた KPI、離脱の予兆でしかない。Today One では「今日は難しい」ボタンが6分類の理由を必ず1つ回収するため、**未実行が最も情報量の多いラベル付きデータに変換される**。「文脈 → 提示行動 → 実行可否 → 理由」という4つ組は、外部から購入することも、後発が短期に模倣することもできない。データの堀はここに掘られる。

> **REFRAME**: 「今日は難しい」は離脱防止の逃げ道ではなく、**本製品における主要なデータ採取装置**である。営業資料でも社内の KPI 設計でも、この位置づけで扱うこと。押されるほど賢くなる構造を、隠さず正面から説明する。

### ASSET 3 — 分離された制約系

Console は「System Constraint：本人 Fit 学習から分離」と宣言している。安全上の制約と、個人への最適化を、同じ学習器で混ぜない。地味だが、後に医療専門職や規制当局へ説明する局面で、この分離があるかどうかが監査可能性を決める。設計時点で持てている点は率直に強み。

## 03. 売る場所 — 制度に空いている3〜6ヶ月

日本の特定保健指導は、初回面接で計画を立て、数ヶ月後に実績評価を行う構造。制度上、初回面接と最終評価には医師・保健師・管理栄養士の関与が求められる一方で、**その間の数ヶ月は事実上、対象者が一人で放置される区間**になりがちである。完了率が上がらない主因もここにある。

> **THESIS**: Today One が売れるのは保健指導の代替ではなく、初回面接と実績評価のあいだに空いた3〜6ヶ月の無人区間である。

この読み替えは、製品の形とも収益構造とも噛み合う。日次1行動・状態適応・軽量な代替提示という設計は、まさに「専門職が横にいない期間を、価値を下げずに走らせる」ための形である。専門職を置き換えないため薬機法・保健指導制度上の摩擦が小さく、既存の保健指導事業者とは競合ではなく**補完**として組める。参入角度としては、正面衝突を避けつつ最も予算に近い位置。

> **MARGIN CONSTRAINT**: 裏返せば、専門職の人的関与は制度要件として残る。**粗利は完全無人型 SaaS の 80% 台ではなく 55〜70% を前提に置くこと。** 人的コストをゼロと仮定した計画は、この領域では必ず崩れる。

## 04. 競合ポジショニング

健保組合向けの既存プラットフォーム（JMDC の Pep Up、DeSC ヘルスケアの kencom など）は制度と接続済みだが、動機づけの中心はポイント・インセンティブ。汎用の健康アプリ（あすけん、FiNC など）は個人向けで、制度接続を持たない。**「制度に接続され、かつ行動の健康価値を担保する」象限は空いている。**

|  | ポイント・報酬で動かす | 行動価値を担保して動かす |
|---|---|---|
| **制度接続** | Pep Up / kencom | **← 空白象限（Today One）** |
| **汎用ウェルネス** | あすけん / FiNC | 歩数・ウェアラブル系（計測は精密、処方はしない） |

この象限を取りにいく際の一行は明快。**「ポイントで動かすのではなく、その人が今日できて、かつ健康価値のある行動だけを出す」**。ポイント設計は原資が続く限りしか効かず、原資が切れると実行率も切れる。Gate は原資に依存しない。

※各社の配置は公開情報に基づく定性的な整理であり、提案前に最新のサービス内容で再確認が必要（付録参照）。

## 05. 買い手と参入順序

| チャネル | 買い手 | 買う理由 | 着手 |
|---|---|---|---|
| **① 健保組合** | 健康保険組合・共済 | 特定保健指導の実施率・完了率が後期高齢者支援金の加算減算に直結し、改善に金銭的動機がある | 即時 |
| ② 企業人事 | 健康経営に取り組む中堅・大企業 | 健康経営優良法人の認定要件と、施策の実効性を示す社内説明の材料が要る | ①と並行 |
| ③ 保健指導事業者 | 特定保健指導の受託事業者 | 完了率が収益に直結。空白期間の充填レイヤーとして OEM 供給 | 6ヶ月後 |
| ④ 個人（B2C） | 一般ユーザー | 収益源としてではなく、認知の入口と拒否データの採取源として維持 | 無料で継続 |
| ⑤ エンジン供給 | 他アプリ・製薬アドヒアランス | Gate ＋ Fit を部品として供給。H2/H3 実証後のオプション | 18ヶ月後 |

①が本命である理由は単純で、**唯一「改善しないと損をする」買い手**だから。実施率が低い健保組合は支援金負担が増える構造にあり、提案は「良い施策です」ではなく「その負担を減らします」という形に翻訳できる。②③はここで作った実績をそのまま持ち込める隣接市場。

## 06. 価格設計

2本立てにする。制度予算に直接乗る対象者課金を主、全社員向けの月額を従とし、健保組合には両方を束ねて提案する。

| モデル | 単位 | 基本 | 成果連動 | 成果条件 |
|---|---|---:|---:|---|
| **A. 保健指導 空白充填** | 対象者1名 / 6ヶ月 | ¥12,000 | +¥6,000 | プログラム完了で加算 |
| A'. 動機付け支援 相当 | 対象者1名 / 6ヶ月 | ¥6,000 | +¥3,000 | 同上 |
| B. 健康経営 全社員 | 1名 / 月（PMPM） | ¥200 | — | 年額 ¥2,400 / 名 |

設計の要点は、**成果連動を「アプリ利用回数」ではなく完了率に紐づける**こと。Console が既に「アプリを使った回数ではなく、健康行動が続いているか」を指標にしている以上、価格もその定義に合わせるのが一貫する。74% 対 61% のリフトは、この成果連動枠を強気に置くための交渉材料になる。

> **PRICING RULE**: Gate（健康価値 70/100）は**いかなる下位プランでも機能制限の対象にしない**。安いプランでは基準を緩める、という設計を一度でも入れると、資産2で述べた差別化が丸ごと消える。「価格は下げても、基準は下げない」を価格表に明記する。

## 08. パイロット設計とKPI

パイロットの目的は売上ではなく、次の顧客に見せる証拠を作ること。したがって測定設計を先に決め、契約書に測定条項を入れてから始める。

| 階層 | 指標 | 比較対象 | 目標 |
|---|---|---|---:|
| **主要** | 特定保健指導の完了率 | 同一健保の前年同期 | +15pt |
| 副次 | 12週継続率（週1回以上の実行） | Fixed 群 | ≥ 60% |
| 副次 | Gate 通過行動のみでの実行率 | Fixed 群 61% | ≥ 70% |
| 運用 | 対象者1名あたり人的工数 | 従来の保健指導運用 | −40% |
| 学習 | 個人ルール確定までの日数 | — | ≤ 21日 |

割付は、同一健保内で対象者を Adaptive 群と Fixed 群にランダムに分けるのが最も強い証拠になる。健保側が対照群の設置を嫌う場合は前年同期比較に落とすが、その場合は**結果の主張を「改善が観測された」に留め、因果を主張しない**こと。ここで誇張すると、次の商談で必ず崩される。

## 09. 投資ゲート — H1・H2・H3 に従う

Console は既に投資規律を持っている。事業側もこれを勝手に飛び越えないことが重要。各ゲートに、技術判断だけでなく事業判断を紐づける。

| ゲート | 内容 | 状態 |
|---|---|---|
| **H1 Fit** | 状態に合わせた提示で実行率が上がるか。+13pt のリフトが出ており、実証済みとして営業に使ってよい段階。 | TEST NOW |
| **H2 Learning** | 使うほどルールが賢くなるか。成立まで ML 投資は禁止。事業側では「AI 搭載」の訴求と、エンジン供給（チャネル⑤）の商談を解禁しない。 | WAIT |
| **H3 Persistence** | 効果が続くか。解約率と LTV を決める。成立まで多年度契約の値引きと、大型の営業組織拡大を行わない。 | WAIT |

> **DO NOT**: 「AI が最適化」を今のマーケティングの前面に出さないこと。現時点で売れる価値は**ルールベースの Fit エンジンによる実測リフト**であり、H2 未成立の段階で AI を訴求すると、証明していない効能を語ることになる。規制上の露出も、技術的負債も、同時に増える。

## 10. リスクと、着手前に塞ぐべき穴

**[P0 — 実装]** 現在のコードでは**アバターをタップするだけで、誰でも Learning Console が開く。** 内部の実行率比較、実験仮説、学習済み個人ルール、Gate 閾値がそのまま露出する。商談相手にも競合にも、意思決定ロジックが全て見える状態。認証済み管理者専用画面として分離するか、最低でもビルドフラグの裏に隠すこと。パイロット開始の前提条件とする。

**[P0 — 個人情報保護]** 体力・疲労・行動ログは要配慮個人情報に準じた取り扱いが必要。企業経由で導入する場合、**個人の実行データを雇用主に渡さず、集計値のみを提供する**壁を最初から製品側に実装する。これは倫理要件であると同時に、企業の法務・労組を通すための営業材料でもある。後付けでは通らない。

**[P1 — 薬機法]** 実行率・継続率は行動指標として問題なく使えるが、疾病の診断・治療・予防効果を示唆する表現は避け、生活習慣支援としての訴求に留めること。特に成果連動契約の条文で、効果指標の書き方が過剰にならないよう法務確認を通す。

**[P1 — 事業依存]** チャネル①は制度改定の影響を直接受ける。特定保健指導の枠組みが変われば需要構造も動く。②健康経営と③受託事業者への展開を、分散ではなく**制度リスクのヘッジ**として位置づけ、2年目までに売上の3割を①以外から取ることを目標に置く。

## 11. 90日アクションプラン

### DAY 1—30（プロダクト＋事業開発）
- Learning Console を管理者認証の背後に隔離（パイロットの前提条件）
- 個人データと雇用主向け集計の分離を設計に反映
- 既存リフト実績を提案書1枚に圧縮
- 設計パートナー候補を健保組合2〜3件リストアップ

### DAY 31—60（事業開発＋法務）
- 1社と有料パイロット契約（測定条項を必ず含める）
- Adaptive / Fixed の割付設計を健保側と合意
- A＋B 併用の料金モデルを実地で提示・検証
- 成果連動条項の文言を法務レビュー

### DAY 61—90（事業開発＋データ）
- 完了率・継続率・人的工数の中間データを回収
- H2（学習で改善するか）の検証を開始
- 2社目・3社目の商談に初期実績を投入
- 受託事業者向け OEM 提案の初稿を作成

## 付録 — 前提条件と要検証事項

本提案はプロトタイプのコード読解と、日本の健康施策市場に関する一般的な構造理解に基づく。以下は**提案前に一次情報で確認が必要**な項目。

- **制度の詳細**: 特定保健指導の実施要件、初回面接・実績評価の運用、後期高齢者支援金の加算減算の現行ルール（第4期の最新版）は、厚生労働省の一次資料で確認すること。本文の記述は構造の説明であり、条文の引用ではない。
- **市場規模**: 健保組合数、対象者数、保健指導の外部委託相場は、健康保険組合連合会などの公表統計で裏取りが必要。第6章の価格は**相場の仮置き**であり、実勢価格の確認前に提示しないこと。
- **競合各社**: 第4章の配置は公開情報に基づく定性的整理。各社の現行サービス内容・価格・健保組合での導入実績は、商談前に再確認すること。
- **収益計画**: 第7章の数値はすべて試算であり、実データに基づく予測ではない。顧客数・ACV・粗利率のいずれも、初回パイロットの実績で全面的に置き換える前提の暫定値。
- **Console の数値**: 74%／61%／+13pt／+18pt などはプロトタイプ内の表示値。実データに基づくものか、デモ用の想定値かを社内で確認してから営業に使用すること。**ここが想定値のまま外に出ると、事業全体の信頼が崩れる。**
